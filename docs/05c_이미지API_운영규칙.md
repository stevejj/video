# 05c. 이미지 API(Nano Banana) 운영 규칙 (v1.0)

> 2026-09-16 사용자 결정: 이미지는 Gemini 앱 수작업 대신 **Google Nano Banana API**로 내가 생성한다. 충전 10,000원.
> 원칙: **한 장씩 생성 → 보여주기 → 사용자 판단**. 배치는 사용자가 범위를 지정한 경우에만, 리스크·예상 비용을 적고 "진행할까요?"를 물어 "알겠다"를 받은 뒤 실행.

## 0. 분담 (2026-09-16 확정)
- **참조용 이미지**(캐릭터 시트, 표정 시트, 부위 참조, 스케일 시트): 사용자가 Gemini 앱에서 무료 생성 → 업로드 → 내가 검수·워터마크 제거·저장. 장수가 적음.
- **영상용 이미지**(공간 기준 컷, 컷별 시작·끝 프레임): API로 내가 한 장씩 생성(생성 요청서 → 승인 → 실행). 장수가 많음.
- 운용 방식 (가) 확정: 캐릭터 없는 공간 기준 컷은 Lite, 캐릭터가 들어가는 프레임은 Flash, Pro는 Flash 2회 실패 컷만.
- 부위 참조 시트(P-1~P-4)는 만들지 않는다. 기존 이미지로 대체: 발 = 고해상도 정면·팽미순 앉기·걷기, 날개 = 컵 들기·정면, 털뭉치 = 캐릭터 시트.

## 4. 절차 (v1.1, 2026-09-16 사용자 규칙 추가)

### 4.0 분담 기준과 사전 검토 (2026-09-18 사용자 지시, 최우선)
1. **난이도 분담**: 내가 API로 만드는 것은 **첫 시도 통과 예상이 "높음"인 컷만**. 중간 이하(새 구도, 새 동작, 소품 상태 변화, 크기 판정이 어려운 컷)는 사용자가 앱에서 만든다.
2. **호출 전 자체 검토**: 프롬프트를 짠 뒤 4.2 체크리스트를 스스로 돌리고, **우려스러운 점·리스크가 하나라도 나오면 호출하지 말고 사용자에게 의견을 구한다.** 검토에서 깨끗할 때만 요청서 단계로 간다.
3. **실행 전 허락**: 요청서에 모델·해상도·비율·참조·프롬프트 전문·규칙 검토 결과·**단가와 누적·잔여 예산**을 적고, 사용자가 "진행"이라고 해야 호출한다. 자동 재시도 0회(4.3).

### 4.0b 사용자에게 프롬프트를 줄 때 (2026-09-18 사용자 지시)
- **재생성 프롬프트는 언제나 전문으로 준다.** "첫 문단만 교체" 같은 부분 제공은 복붙이 불편하므로 하지 않는다. 바뀐 부분이 한 줄이어도 처음부터 끝까지 한 덩어리로 낸다.
- 첨부 파일은 매번 순서대로 전부 보낸다(사용자가 아이폰 사진 앱에서 파일명을 확인하기 어려움). 중복이어도 다시 보낸다.

### 4.1 한 장 생성 전: 생성 요청서
이미지 한 장을 만들기 전에 아래 **생성 요청서**를 보이고, 사용자가 "진행"이라고 해야 실행한다.

| 항목 | 내용 |
|---|---|
| 컷 ID·목적 | 예: 1-01 시작 프레임 / 공간 기준 컷 B1 아침 |
| 모델·해상도·비율 | 예: gemini-3.1-flash-image, 1K, 9:16 |
| 참조 이미지 | 파일명 목록(캐릭터 참조 / 공간 기준 컷 / 부위 시트 / 이전 프레임) |
| 프롬프트 전문 | 그대로 |
| **규칙 검토** | 아래 4.2 체크리스트 결과: 통과 항목 요약, 우려 항목, **추가·수정이 필요한 규칙 제안**(있으면) |
| 예상 비용 | 이 장 단가 + 누적 지출 + 잔여 예산 |
| 배치 후보 | 이 이미지가 통과하면 같은 참조로 만들 수 있는 컷 목록(4.4) |

### 4.2 프롬프트 규칙 검토 체크리스트 (내가 생성 전에 스스로 돌린다)
- 캐릭터(01): 설명 블록이 바이블과 글자 단위로 같은가, 표정 ID가 시트에 있는가, 금지 항목(눈썹·손가락·옷·이펙트) 부정문이 들어갔는가
- 부위(R10): 발·날개·털뭉치 문장이 들어갔는가, 부위가 크게 보이는 컷이면 부위 시트를 첨부했는가
- 스케일(R9): 기준 물체와 상대 크기 문장, 프레임 점유율, 스케일 시트 첨부
- **상태 연속성(R25)**: 위치·개수·양·개폐/전원·흔적 5항목을 앞 컷과 대조했는가. 바뀐 것을 "지금 상태 + 왜"로 적었는가. `Keep everything the same`이 변경 항목까지 붙잡고 있지 않은가
- 물건(R5~R8): 인벤토리 전 항목이 개수와 함께 들어갔는가, 닫는 문장("그 외 없음")이 있는가, 동작 대상이 "이미 있는 그 물건"으로 지칭됐는가
- 공간(02): 기준 컷 첨부, 구도 번호와 카메라 높이 일치, 시간대 조명 문장
- 공간 기준 컷이면(S3-0): 이 공간에서 캐릭터가 쓰는 소품 목록과 캐릭터 자리를 적었는가, 소품이 자리 기준으로 배치됐는가
- 공간 기준 컷이면(S3·W28): **S3 검증표(평면도·프레임 예측·현실 5문·프레임 밖 목록)가 프롬프트 위에 있는가**, 치수·맞은편 거리·앵커·닫힘 문장·프레임 밖 부정문이 있는가, 빈 공간 지정 문장이 없는가
- 구도(02a): 9:16, 세이프존 문장, 컷 크기, 눈높이
- 상식(03): R1 문, R2 날개 점유, R4 물리 가능성, R14 반사 없음
- 세계관(02b): 사람 규칙, 글자 없음, 화면 빈 화면
- 끝 프레임이면: 시작 프레임 첨부 + "같은 물건·개수·색, 자세만 변경" 문장
- 확대·구도 변경 컷이면(S2): 자세가 공간 기준(베개·창 쪽)으로 쓰였는가, "카메라를 본다"류 문장이 없는가, 카메라 방향 유지 문장이 있는가
- **이 컷이 기존 규칙으로 안 덮이는 상황인가?** → 있으면 신규 규칙 제안을 요청서에 적고, 사용자 승인 후 규칙집에 추가

### 4.2b 검수 보고 형식 (R24)
정체성 항목(부리 색·머리 색·털뭉치·볼터치·발·날개·질감) 불합격이면 **선택지를 제시하지 않고 "재생성 권장"을 먼저 쓴다.** 후처리 보정은 배경에만 허용된다.

### 4.3 생성 후
결과 이미지 + 06 체크리스트 검수 결과(통과/불합격 항목) + 실패 시 원인 추정과 수정안. 채택·재생성·폐기는 사용자가 정한다. 내 판단으로 재생성하지 않는다.

**재시도 규칙 (2026-09-18 명시, 사용자 지적)**
- **자동 재시도 0회.** 실패해도 그 자리에서 다시 만들지 않는다. 한 장 만들고 멈춰서 보고하고, 사용자가 "다시"라고 해야 재생성한다.
- 실패한 생성도 **생성 시점에 과금**된다. 재시도는 그만큼 비용이 추가된다(Pro 188원/장).
- 배치 중에도 같다. 첫 장에서 실패가 보이면 나머지를 멈추고 보고한다(4.4).
- 이 규칙은 Kling 운영 규칙의 "재시도 컷당 1회, 컷마다 승인"과 같은 취지다.

**API를 쓸 실익 (2026-09-18 재평가)**
- 통과율은 앱과 같다(프롬프트를 쓰는 주체가 같으므로). 검증 왕복 횟수도 같다.
- 남는 이점은 하나뿐: 사용자가 앱에서 만들어 올리고 내가 받는 **손품이 없어지는 것**. 앱은 0원, API는 장당 188원 + 실패분.
- 따라서 기본은 앱. API는 (1) 사용자가 바빠 앱을 못 열 때, (2) 끝 프레임처럼 내가 저장한 파일을 바로 참조로 넣어야 해서 앱에서는 다시 내려받아 올려야 하는 경우에만 쓴다.

### 4.4 배치 지시 기준 (사용자가 뭘 보고 지시하는가)
- 사용자는 배치 기준을 스스로 만들 필요가 없다. **내가 통과된 이미지마다 "이 이미지를 참조로 물려받는 컷 목록"(배치 후보)을 제시**한다.
- 배치 후보의 조건: 같은 공간·같은 구도 번호·같은 시간대·같은 캐릭터 구성이고, 통과된 이미지를 그대로 참조로 넣어 만들 수 있는 컷. 예: 공간 기준 컷 O1 낮이 통과 → 4-01, 4-03, 6-03 시작 프레임이 후보.
- 사용자는 목록을 보고 "다 진행" / "4-01만" / "안 함" 중 하나로 답한다.
- 배치를 실행하기 전에 내가 반드시 적는 것: 범위, 장수, 예상 비용, **리스크(앞 장 결과를 못 보고 만드는 데서 오는 것: 같은 오류가 N장에 반복될 가능성, 체이닝 컷은 앞 컷 끝 프레임이 확정돼야 하므로 배치 불가 등)**, "진행할까요?" → "알겠다" 후 실행.
- 배치 안에서도 한 장씩 순차 생성하고, 첫 장에서 명백한 실패(캐릭터 붕괴 등)가 보이면 **멈추고 보고**한다. 나머지를 자동으로 밀어붙이지 않는다.
- 배치 불가: 체이닝 컷의 다음 시작 프레임(앞 끝 프레임 확정 필요), 새 공간의 첫 컷, 둘 컷의 첫 장, 신규 규칙 제안이 붙은 컷.

### 4.4b 편집 수렴 (S1)
통과본이 있으면 재생성 대신 편집 요청으로 한 항목씩 고친다. 편집마다 실측·검수. 다른 것이 바뀌면 그 편집은 폐기.

### 4.5 앱 생성 이미지 검수 절차 (스케일·구도)
1. 원본을 `assets/.../original/`에 저장, 우하단 워터마크 제거본을 정식 파일로 저장.
2. `python3 tools/check_scale.py <이미지> --cols <측정할 x 좌표들>`로 격자 이미지와 세로 에지 좌표를 뽑는다.
3. 캐릭터 키(털뭉치 끝~발바닥)를 기준으로 대상 높이의 비율을 계산해 지시값과 비교한다. 바닥 접점은 물체마다 다를 수 있으므로 각 물체의 상단·하단 차이로 높이를 잰다.
4. 결과를 02 공간 바이블 실측 표에 기록하고, 다음 프롬프트는 실측으로 검증된 문장을 복사한다.

## 5. 키 관리
- API 키는 환경변수 `GEMINI_API_KEY` 또는 저장소 루트 `.env`(gitignore 됨)에만 둔다. 채팅·문서·커밋에 넣지 않는다.
- 권장 전달 경로: Claude Code 환경 설정의 환경변수. 채팅으로 주면 .env에 옮기고 채팅 기록에 남으므로 작업 후 키 교체를 권장.

## 6. 실제 사용 기록
### 6.1 첫 호출 — 4-03 시작 프레임 (2026-09-18)
| 항목 | 값 |
|---|---|
| 모델·해상도 | gemini-3-pro-image, 1K, 9:16 |
| 참조 | 4-01 통과본 + 창수 고해상도 정면 + 04 째려봄 |
| 결과 | **1회 통과**. 카메라 방향 유지(S2), 표정·금지 항목·털 결 전부 통과 |
| 소요·비용 | 14초, 191원(출력 188 + 입력 토큰 1,114개 → 3원) |
| 누적 | 191원 / 잔여 9,809원 |

**확인된 것**
- Pro API 품질이 앱 Pro와 동등하거나 낫다. 털 결이 특히 잘 나왔다.
